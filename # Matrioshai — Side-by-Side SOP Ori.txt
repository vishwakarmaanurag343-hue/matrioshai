## New feature to fold in: auto file-discovery ("sandbox find")

**What it is:** person types something like *"I have the doc in my Projects folder"* — no manual upload — and the system searches local/connected storage, locates the matching file, and attaches it to context automatically.

| Aspect | Detail |
|---|---|
| **Where it belongs** | Extension of **1.2 Private Knowledge Base**, not a new layer. The ingestion pipeline already exists; this adds a *discovery* step in front of it. |
| **How it should work** | 1) Small local model parses the reference ("third folder," "Projects folder," "that PDF from yesterday") into a filesystem/query intent. 2) A local file-index (built once, updated incrementally — like a local search index, not a live filesystem crawl on every request) resolves the intent to candidate file(s). 3) If one clear match → auto-attach. If ambiguous → ask the person to confirm which file, don't guess silently. |
| **Sandbox requirement** | This needs an actual sandboxed scope — a whitelisted set of folders the user has explicitly granted access to (e.g. via an OS-level file picker / scoped permission), not blanket filesystem access. "Find it automatically" should never mean "search the entire disk by default." |
| **Privacy gatekeeper interaction** | Once a file is found, it still goes through the **same PII redaction path (Section 2.2)** as any manually uploaded doc before anything reaches the cloud zone. Auto-discovery changes *how the file gets in*, not what happens to it after. |
| **Recommended roadmap position** | **v1 — build alongside 1.2**, since it's a UX layer on top of something you're already building, not new infrastructure. Low cost to add now; expensive to bolt on later once ingestion is built without it. |
| **Reality-check flag** | Silent/ambiguous auto-attach is the risk — if two files could match, resolving to the wrong one and sending it to a cloud LLM is a real privacy failure mode, not just a UX annoyance. **Always confirm on ambiguity; never auto-attach on best-guess.** |

| # | Item | Where | Verdict | What to do instead |
|---|---|---|---|---|
| 1 | Instagram browser automation for notifications/DMs | 6.6/6.8, batch 4-C | **High risk, not "best effort"** — unofficial browser automation on Instagram carries a real double-digit annual suspension rate, and Meta has escalated enforcement sharply through 2026, including going after the tools/libraries themselves. | Make Instagram explicitly **opt-in with a clear risk warning**, not a silent fallback tier. | 3 | "Real-time" notifications across every connected platform | 6.1, batch 4-A/C | **Overstated for most platforms** — most personal-account platforms have no real webhook, so "real-time" becomes constant polling, which fights the lightweight goal directly. | Split explicitly: **webhook-based (Slack, Gmail push, Telegram Bot API) = near-real-time**; everything else = **periodic check**, and say so in the UI, not just internally. |
| 4 | Full stack running concurrently (local LLM + vector DB + OCR + ASR + browser + multiple pollers) while promising low RAM | Whole project | **Needs an explicit resource budget**, not just "each piece is free and light" — they add up. | Set a target (e.g. "idle: <500MB, active local-LLM query: <2GB") and design against it, not against feature completeness alone. |

## Feasibility audit round 3 — corrections from founder feedback

| # | Original flag | Correction | New verdict |
|---|---|---|---|
| 1 | Instagram browser automation — high ban risk | Use **OS-level notification listening** instead of browser automation, for platforms with a real desktop app. **Windows** has an official, sanctioned API for this (`UserNotificationListener` — reads any app's notifications, with explicit user permission). **Mac has no equivalent public API** for reading other apps' Notification Center content, and Apple tightened third-party notification rules again in March 2026 — the only workarounds are undocumented/fragile. Also: **Instagram has no official Mac/Windows desktop app**, so this technique doesn't apply to it regardless of OS. | **Add OS-native notification listening as the v1 approach for Telegram/Slack/WhatsApp Desktop on Windows (full support via UserNotificationListener). On Mac, use each platform's own official API instead of Notification Center reading. Instagram stays excluded — no official desktop app for either OS.** |
| 2 | "Zero-touch" travel booking — CAPTCHA blocks full automation | Confirmed design: AI automates everything up to the CAPTCHA/confirmation step, **pauses, hands control to the user, resumes after** they clear it. | **Resolved.** This is the actual v1 flow — human-in-the-loop at the CAPTCHA checkpoint, not autonomous end-to-end. |
| 3 | "Real-time" notifications overstated for most platforms | Per-platform reality: **Telegram** has a genuinely official real-time API (MTProto via Telethon/Pyrogram, or Bot API) — no browser tab needed at all. **Slack & Gmail** have official push (Events API, Pub/Sub). **WhatsApp** has no official personal-use API — an already-logged-in WhatsApp Web session (the "logged-in tab" idea) is the realistic fallback here, with moderate (not zero, not severe) unofficial-use risk. **Instagram** — same idea reduces back to browser automation, which stays excluded per #1. | **Real-time is achievable and honest for Telegram, Slack, Gmail via their official APIs. "Logged-in tab" fallback applies specifically to WhatsApp, not as a general-purpose technique across all platforms.** |
| 4 | OCR — recommended Tesseract/PaddleOCR over a custom model | Correction: the original flag was about **not building a model from scratch**, not about mobile models being unable to run on desktop — desktop has more compute than mobile, not less, so an existing working mobile model will run at least as well on Mac/Windows. Only the file format matters: **TFLite/ONNX → cross-platform via ONNX Runtime/LiteRT, no rebuild.** **CoreML → Mac-native only, needs conversion to ONNX for Windows.** | **Reuse the existing mobile OCR model on desktop — drop Tesseract/PaddleOCR from the plan. Confirm the model's format (TFLite/CoreML/ONNX) to determine if a Windows-side conversion step is needed.** |

## Section 8 — Founder/CEO daily-use gaps (new, from usage-pattern review)

### Why this section matters
Every item above is small individually, but collectively they're the difference between a tool the founder has to **operate** (check tabs, remember to ask) versus a tool that runs **alongside how a founder actually thinks** (surfaces what matters, remembers commitments, protects time). Section 8.1 (daily operations) is the stronger v1.1 candidate set — concrete, high-frequency pain points. Section 8.2 (thinking level) is lower-frequency but higher-leverage — worth prototyping the decision log early since it's cheap and reinforces the persona-pillar feature you've already committed to.

## Founder spec batch 5 — "Memorize" button (page snapshot + dated log)

| # | What was described | Maps to | Refinement it adds |
|---|---|---|---|
| A | Side-panel "Memorize" button — while on any logged-in page (LinkedIn profile, e-commerce dashboard, etc.), one click summarizes the page and saves it as a note | **6.6 Browser co-pilot + 6.2 Notes command center**, merged | This generalizes the e-commerce daily-tracking idea from 6.8 into a **universal capture action** usable on any page, not just commerce dashboards. |
| B | Entries organized by date/time — "on each day, if a page was memorized, it stores there" | **1.1 Memory core**, new structured object type: **dated snapshot** | Same pattern as the "open loop"/decision log objects proposed in Section 8 — a snapshot record with `{date, time, source_url, platform, summary}`. Notes page should support a **daily/timeline view** so a person can look back and see what was captured each day. |

### Why this is lower-risk than earlier browser-automation concerns

| Earlier flagged pattern (round 3 audit) | This feature |
|---|---|
| Background automation, no user present | **User is actively on the page, initiates the action themselves** |
| Polling/scraping without a human trigger | **One-shot capture, on demand, no repeated automated interaction** |
| Closer to bot behavior Meta/LinkedIn actively detect | **Closer to a browser clipper extension (Notion Web Clipper, Evernote Clipper) — reads what's already rendered, doesn't drive the session** |

**Verdict: safe to build as a v1/v1.1 feature.** This doesn't carry the same ban-risk profile as the earlier-flagged autonomous browsing patterns, because the person is present and the action is explicitly triggered, not backgrounded.

### Practical value this unlocks
- **Manual trend tracking without automation risk** — memorize LinkedIn weekly → follower/engagement trend over time, no background polling needed.
- **Works for platforms that will never get an API or safe automation path** (LinkedIn is aggressive about scraping detection too) — this sidesteps that entirely, since it's user-present capture, not automated reading.
- **Doubles as a lightweight answer to the "real-time notification" problem for platforms without one** — instead of automating notification reads, the person just memorizes the page when they check it themselves, and the system remembers so they don't have to.

### Recommended roadmap position
**v1.1** — this is a natural pairing with the browser co-pilot (6.6) once that's being built for pack #2, and it's genuinely cheap: one button, a summarization call, a dated note. Higher value-to-effort ratio than most of the batch-4 items.
